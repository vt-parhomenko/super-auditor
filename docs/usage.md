# Як користуватись

## Словник

Застосунок працює зі стандартами, а вони написані англійською аудиторською мовою.
Ось відповідники — щоб не спотикатись об терміни.

| В інтерфейсі | В стандарті | Що це насправді |
|---|---|---|
| **Специфікація** | Standard | Документ замовника з вимогами, напр. Tesco Ornamental Plant Standard |
| **Вимога** | Clause | Один пронумерований пункт стандарту: `10.3` + його текст. Їх 183 |
| **Секція** | Section | Тематична група вимог: `10 Pest management` |
| **Документ** | — | Твій внутрішній документ: SOP, політика, інструкція |
| **Профіль виробництва** | Site | Об'єкт, що проходить аудит: цех, склад, площадка |
| **Прогін** | Audit | Одна перевірка: набір документів проти версії стандарту |
| **Finding** | Finding | Результат по парі «вимога × документ» |
| **Прогалина** | Gap | Вимога, якої не покрив жоден документ |
| **Доказ** | Evidence | Дослівна цитата з документа, що підтверджує вердикт |

Два уточнення, які плутають найчастіше:

- **«Вимога» ≠ «пункт».** Вимога — це `10.3` цілком. Усередині неї може бути
  буліт-список: «вимога 10.3 містить 9 пунктів», і документ мусить закрити всі дев'ять,
  інакше це `partial`, а не `compliant`.
- **«Профіль виробництва» не про вебсайти.** У стандарті слово `site` трапляється
  193 рази й означає фізичний об'єкт: *"The site must have a documented policy…"*.
  Аудит проходить об'єкт, а не юрособа — у компанії з трьома цехами це три окремі аудити.

## Швидкий старт

```bash
npm install
npm run rebuild:electron    # зібрати better-sqlite3 під ABI Electron
npm run dev
```

Відкриється вікно застосунку. Шлях до сховища друкується в консоль:
`[super-auditor] сховище: …`

> Якщо збираєшся запускати тести — перед ними `npm run rebuild:node`.
> Причина й симптоми — у [dev.md](dev.md#-нативний-модуль-і-два-abi).

## Сценарій: перевірити одну інструкцію на відповідність стандарту

Приклад: є SOP `Pest Management 0068` і стандарт Tesco. Треба дізнатись, чи відповідає.

### Одноразово — на кожен новий стандарт

1. **Налаштування** → ввести ключ Anthropic.
2. **Специфікації** → «Імпортувати» → PDF стандарту.
3. На картці стандарту увімкнути **«Дозволити хмарні провайдери»**.
   Без цього нічого не запуститься: за замовчуванням чужий стандарт нікуди не надсилається.
4. Відкрити версію → **«Витягти вимоги»** → дочекатись (183 вимоги, кілька хвилин).
5. **Вичитати реєстр**: `J`/`K` — навігація, `Enter` — підтвердити, `F` — позначити проблемною.
   Починай із позначених `flagged`. Поки не вичитано все — аудит не запуститься.
6. *(варто)* **Профілі виробництва** → створити: модулі, сертифікати. Відріже незастосовні вимоги.

### Щоразу, коли треба перевірити документ

7. **Бібліотека** → перетягнути PDF інструкції. Номер і версія підтягнуться з шапки.
8. **Прогони** → «Новий прогін» → обрати стандарт, профіль виробництва і **свій документ**.
9. **«Оцінити»** → подивитись вартість → **«Старт»**.
10. Коли завершиться — вкладка **Findings**.

### Як читати результат

Одна інструкція фізично не може покрити весь стандарт. `Pest Management 0068` стосується
секції 10 — це ~6 вимог зі 183. Решта 177 отримають `not_addressed`, і **це нормально**,
а не 177 порушень.

Тому дивись так:

1. У фільтрі вердиктів **зняти `not_addressed`** — лишиться те, про що документ справді говорить.
2. Читати `non_compliant` і `partial` — це і є зауваження до інструкції.
3. Відкрити finding → праворуч **цитата з документа**, на якій побудований вердикт,
   і поле «Чого бракує».
4. `needs_human_review` — модель не впевнена або спрацював запобіжник. Дивитись очима.

Якщо хочеш побачити відповідність саме по темі документа — постав у фільтрі
**секцію** (напр. `10 Pest management`) замість зняття `not_addressed`.

> **Прогалини** (`gaps`) при перевірці одного документа не дивись — вони показують,
> чого бракує **всьому набору** документів. Вони стають осмисленими, коли завантажиш
> усі інструкції підприємства й запустиш прогін по них разом.

## Подивитись інтерфейс без ключа й без даних

```
npm run dev
```
далі в адресному рядку вікна (Ctrl+Shift+I → Console → `location.hash`) або одразу:

```bash
VITE_MOCK=1 npm run dev
```

Mock-режим наповнює всі екрани реалістичними даними: 183 вимоги, 24 секції,
3 документи, 3 прогони, 168 findings, 100 прогалин. Нічого не зберігається,
жодного виклику до API. Зручно, щоб зрозуміти логіку до того, як заводити реальні
документи.

## Робочий цикл

### 1. Ключ API

**Налаштування** → блок «Провайдери» → ввести ключ Anthropic.

Ключ шифрується через `safeStorage` ОС і в інтерфейс більше ніколи не повертається —
видно лише статус «налаштований». Кнопка «Перевірити» робить найдешевший можливий
запит (список моделей), токенів не витрачає.

Там же — маршрутизація моделей по етапах. Типово:

| Етап | Модель | Чому |
|---|---|---|
| Реєстр вимог | Sonnet 5 | структурний розбір, дешевше |
| Профіль документа | Haiku 4.5 | коротка задача |
| Судження | Opus 5, effort high | тут вирішується якість |
| Критик | Opus 5, effort high | шукає помилки судження |

### 2. Завантажити специфікацію

**Специфікації** → «Імпортувати» → вибрати PDF стандарту.

Код і версія витягуються з імені файлу автоматично:
`20405V5.0EN - Tesco Ornamental Plant Standard 2026.pdf` → код `20405`, версія `5.0`.

### ⚠️ 3. Дозволити хмару для цієї специфікації

**Це найчастіша причина «нічого не працює».**

Кожна імпортована специфікація за замовчуванням має `cloudAllowed = false`, і будь-який
етап із хмарною моделлю відмовиться працювати:

```
Ця специфікація не має покидати цей комп'ютер (cloudAllowed = false)
```

Так зроблено свідомо: на кожній сторінці стандарту Tesco написано
*«supplied for use of the immediate recipient»*, і рішення відправити чужий
стандарт у зовнішній API має бути твоїм явним, а не побічним ефектом імпорту.

На картці специфікації є перемикач «Дозволити хмарні провайдери». Увімкни його —
або залиш вимкненим і налаштуй локальну модель (Ollama / LM Studio) у Налаштуваннях.

### 4. Побудувати реєстр вимог

**Специфікації** → відкрити версію → «Витягти вимоги».

Це Stage 1. Модель посторінково розбирає таблицю вимог; сторінки змісту, вступу
й глосарію відсіюються автоматично й токенів не витрачають. Прогрес видно порядково.

Далі — **обов'язкова ручна вичитка**. Дві панелі: список вимог зліва, редактор справа.

| Клавіша | Дія |
|---|---|
| `J` / `K` | наступна / попередня вимога |
| `Enter` | підтвердити |
| `F` | позначити проблемною |

Вимоги, у яких автоматична валідація знайшла проблему, позначені `flagged` і
показуються першими. Найважливіший сигнал — **пропуск у нумерації** (`10.1` → `10.4`):
він означає, що модель проґавила дві цілі вимоги, а не помилилась у полі.

Поки лічильник «вичитано N з M» не дійде до кінця, кнопка «Позначити вичитаним»
неактивна, а **запуск аудиту заблокований**. Це не формальність: якщо реєстр
кривий, усе далі безглузде, і на рівні результатів це непомітно.

### 5. Завантажити документи

**Бібліотека** → перетягнути файли або «Імпортувати».

З шапки документа автоматично витягуються номер, версія і власник процесу:
`Pest Management 0068 / Versie: 002 / Proceseigenaar: Warehouse & Production Manager`
→ документ `0068`, версія `002`. Якщо документ із таким номером уже є, файл стає
його **новою версією**, а не окремим документом.

Повторний імпорт того самого файлу нічого не створює — дедуплікація за SHA-256 вмісту.

### 6. Профіль виробництва

**Профілі виробництва** → створити.

| Поле | Навіщо |
|---|---|
| Модулі (P / R / O) | вимоги поза scope не потраплять у модель |
| Сертифікати | `ISO 14001` знімає секцію про довкілля, `SMETA`/`SIZA` — Responsible Sourcing |
| Продукти, процеси | контекст |

Кнопка перерахунку покаже результат на кшталт «застосовно 147 зі 183». Це чисті
правила, без AI. Будь-яке рішення можна перекрити вручну — тоді перерахунок його
більше не чіпає.

Профіль не обов'язковий, але без нього перевірятимуться всі 183 вимоги, зокрема
явно незастосовні.

### 7. Прогін

**Прогони** → «Новий прогін» → вибрати специфікацію, профіль виробництва, документи.

Кнопка «Оцінити» показує кількість завдань і приблизну вартість **до** старту.
Оцінка груба (від обсягу тексту), але порядок величини правильний.

Під час прогону видно прогрес по завданнях і поточну суму в доларах.
Прогін можна поставити на паузу, скасувати або продовжити — **план зберігається
в базі до першого виклику моделі**, тож обрив, закриття застосунку чи перезавантаження
не втрачають оплачену роботу. Після перезапуску тисни «Продовжити».

### 8. Результати

**Прогони** → відкрити прогін. Чотири вкладки:

- **Матриця покриття** — теплова таблиця секції × документи. Клік по клітинці
  веде у findings з відповідним фільтром.
- **Findings** — щільна таблиця з фільтрами за вердиктом, severity, секцією, документом.
- **Прогалини** — застосовні вимоги, які не покрив **жоден** документ. Це головний
  вихід продукту: реальні аудити валяться на відсутніх доказах, а не на неправильних.
- **Підсумок** — лічильники, usage, вартість.

### 9. Рев'ю

**Прогони** → прогін → «Режим рев'ю». Розрахований на клавіатуру, бо findings сотні:

| Клавіша | Дія |
|---|---|
| `A` | прийняти вердикт моделі |
| `R` | відхилити |
| `E` | правити |
| `J` / `K` | навігація |
| `Space` | наступний неопрацьований |

Твій вердикт зберігається **окремо** від модельного — модельний не перезаписується
ніколи. Агрегати (матриця, прогалини, підсумок) рахуються по твоєму, коли він є.

Накопичені розбіжності — це майбутній eval-набір, на якому можна буде міряти,
чи стало краще після зміни промпта або моделі.

## Як читати вердикти

| Вердикт | Значення |
|---|---|
| `compliant` | документ явно виконує кожен елемент вимоги |
| `partial` | тему покрито, але бракує окремих елементів |
| `non_compliant` | документ говорить про це і суперечить вимозі |
| `not_addressed` | документ **не про це** — не плутати з невідповідністю |
| `not_applicable` | вирішено правилами профілю виробництва, не моделлю |
| `needs_human_review` | модель не змогла вирішити, або спрацював запобіжник |

**`not_addressed` ≠ `non_compliant`.** Перше живить gap-аналіз (нема документа на цю
вимогу), друге — список невідповідностей (документ є, але поганий).

### Коли з'являється `needs_human_review`

Три механічні запобіжники, які не залежать від моделі:

1. Модель сказала `compliant`, але жодну її цитату не знайдено в тексті документа.
2. Модель узагалі промовчала про вимогу з батчу.
3. Критик не погодився з `compliant` і назвав причину.

У перших двох випадках вердикт понижується автоматично — «відповідає» без доказу
не приймається.

## Типові проблеми

| Симптом | Причина |
|---|---|
| `cloudAllowed = false` | не увімкнено перемикач на картці специфікації (крок 3) |
| Запуск аудиту заблокований | реєстр вимог не вичитаний до кінця (крок 4) |
| `NODE_MODULE_VERSION` | переплутаний ABI — `npm run rebuild:electron` або `rebuild:node` |
| «Модуль ще не підключено» | хендлер IPC не зареєстровано; спробуй `?mock=1` для перевірки UI |
| Прогалин підозріло багато | не заданий профіль виробництва, або документів завантажено менше, ніж покриває стандарт |

## Чого поки немає

- **Експорт у XLSX і PDF** — доступні JSON і Markdown. Замість неповного файлу
  віддається зрозуміла помилка.
- **OCR** — скановані PDF без текстового шару не обробляються; застосунок їх позначає,
  але рушій не підключений.
- **Перегляд PDF з підсвіткою цитати** — цитата й номер сторінки показуються, стрибок
  у документ ще не працює.
- **Оцінка за шкалою стандарту** (5..0) — правила градації витягуються зі стандарту
  й ідуть у промпт, але підсумковий рейтинг ще не рахується.
- **Діфи версій** — БД їх уміє, екрана ще немає.
